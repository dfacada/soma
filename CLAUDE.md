# Dayhub

One app that replaces three: **Glimpse** (encrypted voice journal), **Macros** (food, weight, activity) and **100 Daily Pushup Challenge** (push-up rounds with a leaderboard). Target platform is **Zoho Catalyst**, replacing Vercel + Supabase. URL: **dayhub-onkasary.onslate.com** (Slate's free address, renamed in the Slate console on 2026-11-10; no custom domain yet). The address before it, `soma-onkasary.onslate.com`, stopped working that day and must never come back in an allow-list. Solo project; David is the only developer and also the admin.

**The app was called Soma until 2026-11-10.** Only what a person reads was renamed. Everything underneath keeps the old name and stays that way: the Catalyst project `soma`, the functions `soma_api` and `soma_jobs`, the bucket, storage keys and notification tags (`soma-…`), `SOMA_*` constants, the Telegram bot `@Soma_me_bot` (a bot's username cannot change), the polish tools (`soma-polish`, `soma-critic`, `soma-judge`), and this repo and its folder. (The address did change, later the same day: see above.) `docs/prototype/`, `docs/design/` and `catalyst/SPIKE.md` are records from before and still say Soma. In anything a person reads, write Dayhub, with one capital.

**Dayhub Ops** (`/ops/`, admins only, HANDOFF §12) is where Dayhub is run: issues, people, errors, messages, the audit. What it may show of a person is deliberately small (done or not, never values, unless a reason is given and written to the audit first; never journal text). Every new admin action on someone else's account writes to the audit (`soma_api/lib/audit.js`).

Start with `docs/HANDOFF.md`. It carries every decision made during design, the build plan, the Catalyst spike checklist and the data model. The working prototype in `docs/prototype/soma-prototype.html` **is the spec**: open it in a browser (it runs standalone, state in localStorage). The design canvas source is in `docs/design/`.

## Non-negotiables

- Build directly on Catalyst. **No data migration.** Glimpse, Macros and the Push-Up Challenge stay live on Vercel + Supabase with their data, untouched. Dayhub starts empty; everyone signs up fresh. Glimpse *code* (recording, crypto, IndexedDB recovery, Whisper worker) is still lifted as modules.
- Frontend is Next.js with `output: 'export'` so it deploys to Catalyst Slate as static files. No server components that need a Node server at runtime. All data goes through the Catalyst API function.
- Every API query is scoped by the calling user. Catalyst Data Store has no row-level security.
- Fitbit is the **Google Health API** now (the Fitbit Web API died in September 2026): never build against api.fitbit.com. Steps (in `activity.steps`) and sleep (vault ciphertext, one blob a month in `health_months`); the server makes the Google calls because they need the client secret, and stores neither a token nor any sleep. Google exposes no sleep score; do not invent one.
- Journal entries, audio, photos and Fitbit tokens are end-to-end encrypted (AES-256-GCM, key derived from the vault passphrase in the browser). Food, activity and the round are server-readable so leaderboards and admin fixes work.
- **Never rename the three vault labels** in `src/lib/vault-crypto.ts`: `soma-vault-v1` (the passphrase check), `soma-vault-device-share-v1` (Face ID unlock) and `soma-vault-recovery-v1` (the recovery code). They are part of how every existing vault is checked and unwrapped; change one and a right passphrase reads as wrong, or Face ID and recovery codes stop opening anything. They say `soma` for good.
- **Moves are each person's own** (2026-11-08, `src/lib/moves.ts`): they choose what they track (push-ups, a run, a walk, yoga, a gym session, their own…), each with a daily goal, one of them main. Nobody new starts with push-ups: a first open stores an empty list and Today asks. Settings from before moves read as push-ups (their old target) plus their activity types, unchanged until they choose. Round targets are per person, flat, no ramp. Rest days carry the streak.
- A day closes on five things, in card order: weight, check-in, journal, all four meals, any move (anything logged, even a move since taken off the list; steps only at their goal, and only for someone who chose Steps). Weight is per-person (`requireWeight`, on by default); off means four.
- The day-closing rule lives twice: `src/lib/today.ts` with `src/lib/moves.ts` `movedOn` (the app) and `catalyst/functions/soma_jobs/closing.js` (the server's: the evening nudge and Dayhub Ops; copied byte for byte into `soma_api/lib/closing.js`, `scripts/test-ops.mjs` checks the copies match). Change one, change the other.
- **Every failure is logged.** A `catch` that tells the user something went wrong must also call `report(area, event, error)` (`src/lib/log.ts`); server code that absorbs a failure calls `writeLog` (`lib/log.js`, copied byte for byte into `soma_jobs/`). Never put journal text, a passphrase, a token or a key in a log. David reads it in Dayhub Ops → Errors (grouped into problems, with every row under them).
- Food data (`src/lib/food-data.ts`) is generated from the Macros repo by `scripts/import-macros-data.mjs`. Never edit it by hand and never add invented sample meals.
- Today is the actionable screen: every daily task completes with a tap there. The Journal card is the record button (no floating mic on Today; voice only).
- **Every change a user can notice adds a line to `src/lib/changelog.ts` in the same commit**, in plain words for the person using the app (not a commit message). Same day: add the item at the top of that day's release (What's new shows the lines added since someone last looked, counted from the top). Start each item with a short headline sentence; What's new shows it bold and folds the rest. New day: a new release at the top with a new id. Never change a shipped id. What's new shows unseen releases once on opening; Settings → What's new keeps them all.
- Backfill reaches today and the six days before it (`viewKey` in `Days.tsx`), never further. Streaks and rounds always run on today. A round counts one kind of move, and only what the API froze within two days of the day (`countsForRound` in `routes/days.js`): `round_pushups` for push-up rounds, `round_json` (the day's moves and typed steps) for every other kind; the Google Health sync freezes steps whenever they arrive. What a round counts (`roundAmount`, `ROUND_KINDS`) lives twice: `src/lib/moves.ts` and `soma_api/lib/moves.js`. The board sends only that one number per member, never their other moves.
- Commit and push to `master` directly. No feature branches.

## Design tokens

**Dayhub Night is the default look** (redesign approved 2026-11-02, mock-up https://claude.ai/artifact/2LYXcFvLin2eykr5cgpMCu, plan built in phases: tokens and theme, primitives and floating tab bar, Today with the orb, full-screen moments, the other screens). Night is `data-theme="dark"` (the stored setting kept the name): page `#0B0A09`, surface `#161513`, surface-2 `#211F1B`, ink `#F5F2EB`, muted `#A39E94`; Dayhub's own hues lit to journal `#8F8AF7`, food `#4BCF93`, activity `#F39A57`. Big hero numbers use `dc` (Bricolage condensed, wdth 76, tabular); small numbers stay mono. Motion setting: Lively (springs `--spring`) or Calm (`data-motion="calm"`: no overshoot, no endless loops); `prefers-reduced-motion` still stops everything. Light theme (below) gets the same design on bone.

Bone `#F4F3EF` page, surface `#FFFFFF`, surface-2 `#ECEAE3`, hairline `#DCD9D0`, muted `#6E6A62`, ink `#1B1A17`. Domain hues at equal weight: journal `#5F5BBF`, food `#2C8A5E`, activity `#B7692A`; tints `#ECEBF8` / `#E6F2EB` / `#F6EBDF`. Status colours (admin only): critical `#8E2F24` on `#F3DCD7`, warning `#7A5A0E` on `#F5EBD3`. Type: Bricolage Grotesque (display, 600), Figtree (body), JetBrains Mono (labels and every number, tabular). Cards: 16px radius, 1px hairline, soft shadow. Tap targets ≥ 44px; inputs 16px on mobile so iOS Safari never zooms. Full component vocabulary is in `docs/design/System.dc.html` and the prototype's CSS.

**In code:** tokens are CSS variables in `src/app/globals.css` (never hard-code a hex in a component); components live in `src/components/ui/` (one CSS Module, `ui.module.css`; domain colour comes from the `journal`/`food`/`activity` class setting `--hue`). `/kit` shows every token and component live: add new components there. App code: `src/lib/` (no React: API client, Catalyst session, settings defaults, pure Today logic) and `src/components/app/` (session gate, shell, screens); signed-in routes go in `src/app/(app)/`. All server access goes through `api()` in `src/lib/api.ts`. `npm run dev` runs as the synthetic test member via `.env.development.local`; real sign-in only exists on the Slate URL. No Tailwind, no UI library. Type roles are the global classes `d` (display), `dc` (display condensed, hero numbers), `m` (mono numbers), `eb` (eyebrow label). A new tap that saves or counts something calls `haptic()` (`src/lib/haptics.ts`; `"done"` when it finishes a task): it only fires from inside the tap handler itself, never after an `await`. Sheets close on a swipe down from the handle or title (`ui/Sheet.tsx`), so don't put a draggable control in a sheet's title row.

## Catalyst

Project `soma` (id 120218000000014077, org 939530195, US DC) is linked from `catalyst/.catalystrc`. Deploy functions with `node deploy.js [soma_api|soma_jobs]` from `catalyst/`: it merges the gitignored `catalyst/secrets.json` into each function's env, deploys, and restores `catalyst-config.json`. Never run a bare `catalyst deploy --only functions`: it wipes the secrets from the live function. Never put a secret in `catalyst-config.json`. Deploy the frontend with `npm run build` in the root, then `catalyst deploy slate soma -ni` from `catalyst/` (Dev URL `https://dayhub-onkasary.onslate.com`). The `catalyst-by-zoho` MCP server handles tables, job pools and Authorized Domains (headers `Catalyst-org: 939530195`, `Environment: Development`). **Every table is closed to the browser:** Catalyst gives the App User role SELECT on a new table by default, which lets any signed-in account read every row of it through the Web SDK, approval or not. Dayhub never reads the Data Store from the browser, so right after creating a table set both roles to nothing (`CatalystbyZoho_Update_Table_Permissions`, body `{"App User": [], "App Administrator": []}`). `node catalyst/test-api.js` also runs as a second synthetic member (`x-test-member: 2`) to prove one member cannot reach another's rows; add a check there for every new per-member route. A third (`3`) is filled with data and deleted each run, and a fourth (`4`) starts pending for the invite checks. The test key works only where the gateway says Development. Data Store Text silently truncates at 10,000 chars: enforce lengths in the API. Zoho's official Catalyst agent skills are vendored in `.claude/skills/`; use them as reference, but ignore their "stop until Zoho MCP is connected" gate. The CLI path works and MCP is optional. Findings and verified limits live in `catalyst/SPIKE.md`.
